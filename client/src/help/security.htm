How the connection is secured

The encryption support in Java 1.3 to 5 stops at TLS 1.0 (Java 1.3 has none built in at all) and trusts certificate authorities long since replaced, so a modern server cannot be reached with it. Paste Jar carries its own:

  • TLS 1.2 from Bouncy Castle. The encryption code is built into GWPASTE.JAR, so Java's outdated TLS support and certificate list are not used at all.
  • A pinned server key instead of certificate authorities. The program talks only to a server whose public key matches one of the key pins in Settings. Let's Encrypt certificate renewals make no difference, as long as the server keeps the same key.
  • Modern ciphers. ChaCha20-Poly1305 or AES-GCM, with X25519 or P-256 key exchange. See Connection settings.

Random numbers

Encryption keys need unpredictable random numbers. Java 1.3 makes its own by timing threads, which takes over half a minute on a Pentium-class machine, so the program gathers them instead from Windows' cryptographic random number generator (through GWTRAY.DLL), the seed file PASTE98.RND saved at the last exit, Java's own generator on Java 5, and timing measurements, all mixed with SHA-256. Status shows which sources were used. Windows 95 without Internet Explorer 3.02 or later has no cryptographic generator; the seed file and timing still apply.

Your password

The program asks for your pastes password the first time you send, and keeps it in memory only, until you exit. It is never written to disk, exported or logged. Changing the server's host or port logs you out, so the password is never sent to a different server.

Speed

Setting up an encrypted connection is hard work for a Pentium-class processor. At start-up the program connects once in the background, which takes a couple of seconds; after that, a paste takes about half a second. See Connect at start-up to warm up the encryption code in Connection settings.
